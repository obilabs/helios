## ⚠️ Common Pitfall: "Tenant" vs "Organization" Terminology

**CRITICAL:** You may see some older code or comments mentioning "tenant". **Ignore these - they are legacy artifacts.**

### Use This (Correct):
- ✅ `organization`, `organizationId`, `organization_id`
- ✅ Database table: `organizations`
- ✅ Foreign keys: `organization_id`
- ✅ Variables: `organizationId`, `orgId`

### Never Use This (Legacy):
- ❌ `tenant`, `tenantId`, `tenant_id`
- ❌ Database table: `tenants` (doesn't exist!)
- ❌ Any multi-tenant terminology

The codebase previously experimented with multi-tenant architecture but was changed to single-organization design. Some variable names still reference "tenant" but they actually work with the `organizations` table.

**If you see a file referencing a `tenants` table, it's broken dead code that should be deleted.**

## ⚠️ Dependency Pinning Rules (Learned the Hard Way)

Helios is the basis for Aegis. When creating derived projects, follow these rules to avoid regressions:

### Pin Versions Properly
- **Docker builds without lockfiles** resolve `^` ranges to latest — which may include breaking majors
- `better-auth`: Pin to `~1.4.x` (NOT `^1.4.x`). Version 1.5.x removed `apiKey` from `better-auth/plugins`
- `zod`: Use `^4.1.0` (Zod 4). better-auth 1.4.x requires Zod 4 features (`z.ipv4()`, `z.record()` with 2 args)
- When starting a new project from Helios patterns, copy the **exact** dependency versions, not older baselines

### Helios Baseline Versions (Current)
```json
{
  "better-auth": "^1.4.7",
  "zod": "^4.1.13"
}
```

### API Key Patterns to Port
Helios has typed API key infrastructure that derived projects should replicate:
- `backend/src/utils/apiKey.ts`: typed `API_SCOPES`, `hasPermission()`, timing-safe `verifyApiKey()`, `validateApiKeyFormat()`
- These patterns are more secure than a basic hash-and-compare approach
- Aegis is currently missing these — they need to be ported

## 📒 R&D Documentation (Grant-Critical)

**Required.** After any significant development session, write a summary to `.rd_log/YYYY-MM-DD.md` (gitignored). This is the source of truth for R&D grant claims (e.g., SR&ED) — missing entries are missing claimable hours and unprovable work.

### When to write an entry
- Resolved technical uncertainty (novel integration, debugging, perf, security)
- Tried multiple approaches before something worked
- Made an architecture / library / protocol decision worth recording
- Spent >~1 hour investigating a problem
- Anything you'd want to defend in a grant audit

### Format
```markdown
# YYYY-MM-DD

## [Feature / area worked on]
- **Technical uncertainty:** what was unclear at the start
- **Approaches tried:** enumerate (including dead ends — they count)
- **What worked / didn't:** outcome
- **Time spent:** rough hours
- **Architecture decisions:** if any, with rationale
```

Append to today's file if one already exists — do not overwrite. Entries should reference commit SHAs / PR numbers when relevant so a reviewer can cross-check.

### Workflow integration
- Bake into the build/test cycle: after a feature passes its regression suite, write the R&D entry **before** moving to the next task. Treat it as part of "done."
- The supervisor agent audits `.rd_log/` on session close. Days with significant commits but no log entry get flagged and must be backfilled from `git log` + commit messages.
- Backfilling stale days is acceptable but lossy — write the entry while the uncertainty is still fresh.
